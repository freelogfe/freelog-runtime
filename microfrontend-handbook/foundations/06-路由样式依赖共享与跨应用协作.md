# 基础 06：路由、样式和依赖为什么最容易跨越应用边界

[课程入口](../README.md) · [Vue 原理](04-Vue从编译响应式到应用卸载.md) · [React 原理](05-React从JSX与Fiber到多根生命周期.md) · [进入架构设计](../architecture/01-从需求推导微前端边界与方案.md)

前面的多根实验说明：多个框架 app／root 不需要微前端库就能同页运行。但是地址栏只有一份，CSS 会按实际树匹配，模块依赖可能收敛或重复。真正的装配问题从这里开始。

## 1. 路由库本质上在同步什么

路由至少把四件事联系起来：当前位置、路径匹配、组件树／数据加载、导航与恢复。浏览器只提供其中一部分原语，并不知道“章节播放器路由”。

```text
点击 / navigate
  → 解析目标位置
  → 导航检查、必要的数据准备
  → 更新路由状态与历史
  → 匹配组件树
  → 框架调度与提交
```

不同路由库会安排不同顺序。不能因为两个 API 都叫 beforeEach／navigate 就认为它们有相同的取消或异步合同。业务路由守卫也不替代服务器访问控制。

原生 pushState 改写同源位置和对应历史状态，本身不触发 popstate；用户遍历历史是另一条入口。[History.pushState](https://developer.mozilla.org/en-US/docs/Web/API/History/pushState)是浏览器行为依据。因此适配器需要明确“自己主动导航”如何通知路由库，“浏览器后退”又由谁处理。

## 2. browser、hash、memory 是不同存储策略

| 策略 | 路由位置主要存在哪里 | 对多个应用的影响 |
| --- | --- | --- |
| Browser history | 真实 pathname/search 与 history state | 多个应用需要路径／状态所有权，不是各写各的 |
| Hash history | 真实 URL 的片段 | 仍然只有一份共享 hash，不能凭 hash 自动分区 |
| Memory history | 路由库内部结构 | 不争写地址栏，但分享／刷新／后退如何恢复要另设计 |

[Vue Router 的 history 模式](https://router.vuejs.org/guide/essentials/history-mode.html)与 [React Router 6 的 MemoryRouter](https://reactrouter.com/6.30.3/router-components/memory-router)说明这些策略。这里只比较稳定的存储原理，不把两个库的每个导航或销毁 API 当成相同接口。

例如宿主拥有 `/node/reader`，A 选择 `/chapter/2`，B 选择 `/playlist/3`。如果 A 直接 `history.pushState({}, '', '/chapter/2')`，宿主可能认为离开节点页；如果 A/B 轮流覆盖 hash，也会互相丢状态。

第一种简单设计是宿主独占 URL，子应用使用 memory；第二种是宿主显式把子位置投影到 URL／state，并在恢复时分发；第三种是分配明确基路径给子应用，再协调唯一的真实历史栈。选择取决于分享和后退的产品合同，而不是哪个模式名字听起来更“独立”。

## 3. 地址至少分成五种用途

```text
页面导航地址：用户在哪里，能否复制／刷新
应用入口地址：从哪里下载HTML或entry模块
模块依赖地址：import相对于哪个referrer解析
CSS资产地址：url(...)相对于哪个样式文件解析
业务API地址：服务端识别什么请求与访问上下文
```

把它们统一成一个 base 字符串是常见根因。Vite base 调整产物资源路径，不会自动给所有业务 fetch 加正确 API 前缀；路由 basename 解决路由匹配，不会给原生模块依赖重新指定 referrer；虚拟 location.origin 的返回值也不会改变浏览器请求权限。

解决路径问题时先画 URL 图，再定位由谁生成每条边。只有 HTML 的 script 地址正确，不能证明动态 chunk、CSS font 和 modulepreload 都正确。构建章节的真实 dev／prod 观察可用于检验这些区别。

## 4. 为什么 Vue scoped 与 CSS Modules 都不是 document 隔离

Vue SFC 的 scoped style 通过编译给选择器和相关节点加作用域标记。示意：

```css
/* 源码 */
.title { color: green }
/* 转换后的关系示意，具体哈希由构建决定 */
.title[data-v-example] { color: green }
```

CSS Modules 通常把局部类名映射为构建生成的名字，再让代码使用映射。这两种机制都减小意外选择器冲突，却不会创建另一个 document。`body`／根字号、继承属性、显式 global／deep 规则、共享字体名称与应用外弹层仍需管理。[Vue SFC CSS 特性](https://vuejs.org/api/sfc-css-features.html)明确了 scoped、deep、global 与 slot 的边界。

CSS 冲突也不能只按选择器“越长越强”判断。来源与重要性、cascade layer、specificity、声明顺序等共同影响结果。宿主 reset 与子应用普通规则的胜负，应在实际 Computed 中追到规则，而不是不断叠加 `!important`。[CSS 层叠与 specificity](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity)提供详细顺序。

## 5. Shadow DOM 增强了哪些边界，又保留了哪些关系

Shadow root 能让普通 DOM 查询与选择器匹配有清楚的树边界。它仍与宿主元素连接，继承属性、CSS 自定义属性、事件 retarget／composed，以及外部暴露的 part／slot 都可能形成预期连接。

所以它适合样式与 DOM 封装，不是一个能阻止恶意 JS 访问页面的权限容器。第三方库如果把弹层挂到 document.body，它的弹层也可能离开原 shadow 样式环境。字体、层叠、焦点、定位、无障碍关系还需按实际组件验证。[Using Shadow DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM)是浏览器封装依据。

要决定它是否适合你的应用，至少测试一个弹窗、一个表单焦点流、一个滚动容器、一个相对资产与一次完整退出，而不只放一个彩色按钮。

## 6. Portal 与 Teleport 是样式和所有权的压力测试

同一个应用可以有不止一个物理 DOM 落点。框架依然拥有弹层的逻辑状态，但样式与浏览器事件按物理位置处理；React 又额外提供逻辑树的合成事件传播。

于是父容器清理、框架 root 清理和弹层根清理必须配合。先让组件库支持的 container／appendTo 指向分配的落点，再评估是否需要通用 DOM 重定向。无差别改写 body.appendChild 会同时接管组件库、样式运行时与脚本加载语义，代价很大。

独立基础实验中，React Portal 按钮点到 A 的父合成事件；Vue Teleport 按钮不会因为仍属于原组件上下文，就自动沿原来物理根冒泡。这个对照说明：跨框架设计应该约定“弹层落点与拥有者”，不能依赖两个框架事件机制恰好相同。

## 7. 依赖共享不是去重一个包名

依赖有至少三种身份：源工程选择的包与版本、构建后图中的模块节点、运行时实际对象。相同 package.json 字符串不能保证最后是同一个对象。

| 共享对象 | 可能想共享的原因 | 必须核对的边界 |
| --- | --- | --- |
| React 与 renderer | 让组件 Hook 连接正确 dispatcher，减小下载 | 组件／renderer用到的React对象、版本、初始化顺序 |
| Vue runtime | 统一helper与响应式／渲染环境 | 重复runtime之间的依赖追踪、VNode、scope与注入前提 |
| 路由／store库 | 复用逻辑或共享业务状态 | 是只共享代码，还是还共享一个实例？谁持有退出权？ |
| 组件库与主题 | UI一致、资源复用 | CSS全局规则、弹层服务、宿主订阅和框架 peer依赖 |
| Polyfill／全局patch | 兼容旧环境 | 修改的是共享原型／浏览器API，不能随A退出直接撤销而不考虑B |

React 两套完整且各自配对的 runtime／renderer 可以共存；错误往往发生于跨配对边界使用组件或 Hook。Vue 的共享代码也不意味着两个 app 的 appContext 必须共享。框架章节给出源码依据；这里把它们转化为依赖协商问题。

## 8. 制定依赖策略，而不是只写 singleton: true

三个常见选择：全部内置、宿主共享一组固定依赖、按协议协商共享。每种都应写清版本、失败方式、发布与退出所有权。

全内置增加字节与可能的重复全局行为，但应用根可以更自足；宿主共享降低重复，却增加升级耦合；协商需要处理不满足版本、懒加载时机、share scope与初始化等额外协议。没有一个配置项能跨所有 URL、realm、容器和加载器制造唯一对象。

若跨边界只交换普通数据和能力，远端独立持有框架根，通常比直接交换框架组件和 store 代理更容易控制兼容范围。但这仍是设计取舍，统一技术栈的组件平台也可能主动选择更紧密耦合。

## 9. 跨应用状态与命令应分开设计

“当前章节是 c2”是一份状态；“购买一次”“保存这份编辑”是一项命令。状态可合并到最终值；命令通常需要独立身份、处理结果与去重规则。

如果协议只提供一个异步浅合并对象中心，就不能把连续两次写入当成两条可靠独立命令。反过来，为每次鼠标移动建一条带重试的命令也未必合理。先说明语义，再选机制。

同页函数调用能共享对象与闭包，跨源消息需要序列化与来源校验；两边的返回、错误、取消、订阅和有效期需要适配，不能因为 API 形状都像 send 就混为同一通信架构。

## 10. 把三类共享收束成一份设计检查

对播放器 A/B，分别写出：谁可以写 URL、谁拥有样式落点、哪些依赖代码共享、哪些状态实例共享、谁能撤销订阅。然后执行 A 退出而 B 保留、宿主导航、版本升级和弹层关闭四组反例。
