# 基础 02：执行环境、事件循环与浏览器权限

[上一章：模块系统](01-浏览器模块系统与应用身份.md) · [下一章：构建与运行时加载](03-Vite与Webpack如何决定应用加载.md) · [课程入口](../README.md)

两个应用能各自保存状态，不代表它们不会阻塞对方、不会修改对方的 DOM、不会发起同源请求。设计微前端时，应分别回答：**代码能看见哪些名字、对象来自哪个环境、工作何时执行、浏览器允许它做什么**。

## 1. 词法环境、全局对象、realm、document、origin 不可互换

| 概念 | 它实际管理什么 | 对隔离的含义 |
| --- | --- | --- |
| 词法环境 | 标识符解析到哪个绑定 | 函数／模块可避免名字互相覆盖，不能隔开已共享的对象 |
| 全局对象 | window、document、计时器等可访问属性 | Proxy 可改写经过代理的属性访问，不会改写所有语言与宿主行为 |
| realm | 全局环境与内建对象的一组身份 | 另一个 Array／Function／原型；不自动意味着不同网络权限 |
| document／DOM 树 | 可见节点、事件路径、样式应用对象 | 同一 JS 模块也能操作多个树，多个 realm 也能被适配到同一可见树 |
| origin | 浏览器的协议、主机、端口安全主体 | 由真实文档与请求上下文决定，不由 location getter 的显示值决定 |

HTML 把 realm、全局对象、文档相关环境接起来，还说明可同步相互访问的环境可能在同一 agent 上运行。[HTML 的 realm 与 agent 模型](https://html.spec.whatwg.org/multipage/webappapis.html#realms)是依据。架构上的推论是：创建 iframe 不等于获得一个能与主页面任意并行的 UI 线程，更不能宣称一方死循环不会影响另一方。

独立页面中创建同源空 iframe 后，`frame.contentWindow.Array !== Array`，但你仍可读取它的 document。跨 realm 的 `instanceof` 使用的构造器和原型身份不同；结构检查、`Array.isArray` 等判定可能比拿宿主构造器作比较更合适。DOM 方法还会检查接收者，错误地把 document 方法用代理作 this，可能导致 Illegal invocation。

这些现象说明为何通用运行环境适配器复杂：它既要保留原生 API 的接收者语义，又要改写应用观察到的归属，二者常常冲突。

## 2. Proxy 拦截的是一条访问路径

考虑这段没有任何微前端框架的代码：

```js
const shared = { settings: { language: 'zh' } }
const proxy = new Proxy(shared, {
  set() { throw new Error('top-level writes blocked') },
})
proxy.settings.language = 'en'
console.log(shared.settings.language) // en
```

最后一次写入操作的目标是 `settings` 对象，不是 proxy 本身。阻止顶层 set 不代表嵌套对象被复制或冻结。拿到宿主函数、共享原型、raw document 或预先保存的原生方法，还会形成更多绕过某条代理路径的引用。

同理，with 改变的是一段代码的标识符查找；函数包装会改变顶层声明和 this；这些技术可以兼容可信应用，却不构成浏览器级恶意代码安全边界。`Object.freeze` 也只有其实际冻结对象的边界，浅冻结不会递归处理整张引用图。[Proxy 的拦截目标与限制](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Proxy)可用于核对语言行为。

一个架构评审因此必须写出威胁前提：是合作开发者避免偶然污染，还是需要执行可能恶意的代码？后一种要求不能靠增加几个代理 trap 延续原来的安全承诺。

## 3. 一次交互经历的队列，不等于“异步晚一点”

假设点击处理函数中运行：

```js
console.log('handler:start')
queueMicrotask(() => console.log('microtask'))
setTimeout(() => console.log('timer'), 0)
console.log('handler:end')
```

先执行当前调用栈，再在相应微任务检查点处理 microtask，timer 属于后续任务。0ms 是调度请求，不是精确执行时间。页面渲染更新有自己的机会；不要把“Promise 已完成”或“nextTick 已完成”直接翻译为“用户已经看到绘制”。[HTML event loop](https://html.spec.whatwg.org/multipage/webappapis.html#event-loops)规定任务、微任务与渲染处理的基础框架。

把框架加入之后，至少有三层调度：

```text
浏览器任务／微任务／渲染机会
  ↑ Vue scheduler 或 React scheduler 选择怎样批处理工作
  ↑ 应用自己的请求、状态更新、可见性与业务有效期
```

Vue 的 ref 变更、组件 render effect、DOM patch 与 nextTick 是可区分的阶段；React 的 render、commit、layout effect、passive effect 也不能折成一次函数调用。它们后续章节将沿源码解释。外层加载器收到一个 mount 返回值，并不能凭空知道所有框架工作与业务请求什么时候完成。

## 4. 可中断调度与抢占任意代码完全不同

React 可把自身可切分的渲染工作分阶段调度；浏览器不会因此任意打断插件写的 `while (...)`。同页两个 Vue/React 根也共用很多宿主资源。一段长同步计算可以延迟另一应用的输入、计时与绘制。

如果把计算放入 Worker，需面对它没有直接 document 操作、消息通常需要结构化传输的事实。你能搬过去的是适合消息协议的计算，不是把既有 DOM 应用原封不动搬离主线程。

因此，性能隔离和状态隔离应分别设计。一个根的更新再独立，也不代表它有独立 CPU 预算。宿主要考虑并发应用数、隐藏应用工作、同步初始化峰值，而不是只测单应用首屏。

## 5. 物理事件路径与框架逻辑树

浏览器事件按实际事件路径处理捕获与冒泡。Shadow DOM 还涉及事件是否 composed、跨边界 retarget 以及 composedPath；仅看 event.target 可能看不到内部原节点。[composed](https://developer.mozilla.org/en-US/docs/Web/API/Event/composed)与 [Shadow DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM)说明了这组边界。

框架可再在原生事件之上建立自己的映射。React Portal 物理节点可以位于另一个容器，合成事件却沿原 React 树传播；Vue Teleport 的上下文仍属于原组件树，但原生 DOM 事件不会自动获得与 React 一样的逻辑冒泡合同。

这里不能用“节点被移动”作唯一解释。必须画两棵树：

```text
逻辑树：应用A → Provider／父组件 → 弹层组件
物理树：document.body → 弹层容器 → 弹层按钮
```

由此推导出三份所有权：哪个框架拥有组件状态，哪个容器拥有样式与布局，哪个对象真实持有事件监听。微前端退出时需要沿三者清理，不能只 removeChild 一个根节点。基础实验会对比 Portal 与 Teleport。

## 6. 资源获取至少经过三种协议

| 获取方式 | 谁决定地址与执行 | 重要边界 |
| --- | --- | --- |
| fetch HTML／JS 文本后自行处理 | 应用或加载器 | 得到文本不自动获得模块连接、脚本元素或正确执行上下文 |
| 原生 script／module／动态 import | 浏览器脚本和模块处理 | CORS、MIME、模块 URL／依赖图等规则不能仅靠包装 fetch 替代 |
| iframe 导航 | 浏览器导航与文档模型 | 登录、Cookie、同源可访问性、sandbox 权限是另一套约束 |

一次顶层导航成功不能证明跨源 fetch 成功；一个经典 script 可加载也不能推出 module 依赖同样被允许。若携带跨源凭据，还需满足匹配来源与服务端凭据允许等响应约束；Cookie 另受自身策略限制。[CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)只解决浏览器读取响应的一部分权限，不替代平台业务鉴权。

部署上还有 CSP。运行字符串需要相应策略允许；插入脚本、内联样式和模块资源也有各自策略。架构选择越依赖动态 Function、内联变换，就越应提前写清部署策略，不能等生产环境拒绝后才把安全配置整体放宽。

## 7. 退出应用不是一个 remove()，而是撤销一组关系

把资源按有效期分层：

| 有效期 | 例子 | 谁终止它 |
| --- | --- | --- |
| 模块／代码定义 | 模块表、共享库、静态定义 | 加载与版本策略；不与单实例退出简单对称 |
| 应用实例 | Vue app、React root、实例 store | 对应框架适配器与拥有者 |
| 一次工作 | 请求、章节加载、编辑保存 | 工作令牌、取消信号、错误处理 |
| 宿主长期服务 | 用户订阅表、播放器协调服务 | 服务本身提供 owner／unsubscribe 协议 |

AbortController 不会撤销已提交的 UI，也不会自动停止无关定时器；代次校验不会关闭网络；框架 unmount 不会自动清掉任意模块顶层副作用。每种机制解决一份责任。旧请求案例保留在 [CASE-STUDY](../CASE-STUDY.md)，但读完 React／Vue 的 effect 生命周期再回来看，才能判断哪个清理由框架负责、哪个必须自己写。

## 8. 把本章结论变成架构输入

选择执行环境前，先填写：是否信任代码、哪些对象共享、是否需要原生 ESM、能否接受跨源消息协议、是否要求紧密 DOM 整合、资源与后台工作由谁撤销。

如果这些答案与生产策略不一致，问题还在架构层。一个具体沙箱库只能实现某种组合，不能替你选择这些前提。
