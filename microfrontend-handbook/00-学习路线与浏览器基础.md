全书顺序现已重建为底层技术、独立架构、MicroApp对照、维护。首次学习从 [基础01](foundations/01-浏览器模块系统与应用身份.md) 开始；本页保留的六题主要用于实现层诊断，得分高也不代替Vue／React／Vite与架构验收。新的独立实验在 [FOUNDATION-EXPERIMENTS](FOUNDATION-EXPERIMENTS.md)。

你要解决的实际问题是：主题或插件出了问题，能判断责任层、解释真实调用链，并做出有证据、可回归的修改。本章先帮你找到起点，再建立后续章节共用的浏览器模型。

学习时始终追问三个问题：**谁在运行？它持有哪些资源？离开时谁释放？** 记住答案的来源，比记住文件名更有用。

## 1. 先用六个问题找到自己的起点

先写判断，再写一条能证明判断的观察或源码依据。不确定就记“待验证”，不要先翻答案。

| 编号 | 情境 | 你需要回答 |
| --- | --- | --- |
| D1 | 播放器插件的开发地址独立打开正常，放进节点页面却白屏 | 独立访问成功能排除哪些故障？还有哪些完全没被验证？ |
| D2 | `reader-a`、`reader-b` 都使用 `window.player` 和 `#root` | 要让它们共存，需要分别处理哪两种归属？只隔离 JS 够不够？ |
| D3 | 断点中，同一个应用的 `onLoad` 被调用两次 | 是应用重复启动了吗？怎样区分资源阶段完成和代码已执行？ |
| D4 | 沙箱把子应用看到的 `location.origin` 改成了文件服务域名 | 浏览器会因此允许原来被拒绝的跨源请求吗？ |

评分只用于选路：每题 0—2 分。没有判断或凭猜测为 0；结论正确但不能解释为 1；能说出原因并给出验证办法为 2。对照 [第 14 章](14-自测答案与进阶挑战.md) 后再计分。

## 3. 先把教学场景和真实平台分清

本书的机制实验采用**教学阅读宿主＋`reader-a`／`reader-b` 播放器插件**。宿主负责容器和操作入口，两个播放器让你观察同资源多实例的行为。实验通过 `data` 传递的教学能力用于解释同页对象与函数传递，不等于真实 Freelog SDK 或服务端授权。

真实 Freelog 中，节点主应用是基座，主题本身也是子应用；主题再借运行时挂载插件。不要把“教学宿主”直接等同于“平台主题”。业务身份与能力注入在第 02、09 章接回这张图。

理解一个浏览器页面，先分开这五种对象：

| 对象 | 它说明什么 | 观察时不要混淆 |
| --- | --- | --- |
| `window`／全局对象 | 当前环境可读取、写入的全局属性 | 顶层 `let/const` 不是自动的 `window` 属性 |
| JavaScript realm | 一组全局对象、内建对象和构造器 | 两个 realm 的 `Array` 可以不是同一个构造器 |
| `document`／DOM | 节点树以及创建、查询、插入接口 | JS 分开执行，不会自然得到两棵独立的可见节点树 |
| origin | 协议、主机和端口的组合，用于浏览器同源约束 | 对象表面上返回的 origin 不能改写真实网络权限 |
| 应用实例 | 框架管理的某一次运行状态与名称 | 入口 URL、资源 ID 和实例名回答的是不同问题 |

例如，“播放器 A 是 reader-a”标识运行实例；“A 与 B 来自同一个入口”说明代码来源相同；“A 的根节点属于容器 A”说明显示与操作归属。把这三句话分开，才能分析多实例故障。

### 观察一个新 realm

下面实验在独立空白页的 Console 运行。它只创建、观察并删除一个同源空 iframe，不访问平台服务。

```js
(() => {
  const frame = document.createElement('iframe')
  document.body.appendChild(frame) // about:blank，同源，仅用于观察 realm
  try {
    const other = frame.contentWindow
    const array = new other.Array()
    console.log(array instanceof Array)       // false
    console.log(Array.isArray(array))         // true
    console.log(other.document === document)  // false
  } finally {
    frame.remove()
  }
})()
```

先预测三个输出，再运行。`instanceof` 会沿指定构造器的原型链判断；`Array.isArray` 不依赖当前页面的 `Array` 原型身份。这个差异解释跨 realm 的库兼容问题。

它还不能说明 MicroApp 的业务 DOM 放在哪里。MicroApp 的 iframe 沙箱会组合 iframe 执行环境与主页面可见 DOM 适配；第 05、06 章会追踪这一步。

## 4. 浏览器原本怎么工作，框架才需要拦截什么

先用原生行为预测，再阅读适配层。以下四条将反复出现在排障中。

**脚本有执行语义。** 经典脚本、ES Module 与动态 `import()` 不走同一套作用域和依赖加载规则。模块的静态 `import` 不能直接塞进任意 `new Function()` 包装；模块依赖还要按正确 URL 解析。[scripts.ts](../packages/micro-app2/src/source/scripts.ts) 的 `isTypeModule`、`bindScope`、`runCode2InlineScript` 正在选择这些路径。

**主页面只有一份浏览器历史栈。** 原生 `pushState` 修改地址但不自动发送原生 `popstate`。后退／前进与主动 push 是不同入口，微前端需要协调虚拟 location、真实历史和事件。不要把“页面变了”和“历史记录正确”合成一个验收条件。

**节点移除不会取消所有异步工作。** Promise 完成、请求返回、计时器触发和 DOM 存在与否不是同一件事。最典型的时间线是：A 次挂载开始请求 → 卸载 → B 次挂载先显示新内容 → A 的旧响应迟到。谁仍有资格提交结果，需要明确判断。贯穿推演见 [同一实例的迟到结果](CASE-STUDY.md)。

**代理只作用于经过代理的访问。** `Proxy` 能拦截对象操作，`with` 能调整标识符查找；已经获得的原始引用、共享嵌套对象以及不同脚本执行路径，仍需分别分析。不能由“window 有代理”推出 DOM、存储和平台权限全部独立。

机制依据可查 [Proxy](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Proxy)、[with](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/with)、[同源策略](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy)。本地 fork 的具体实现仍需与代码互证。

## 5. 用一个小模型看懂变量分流

先预测最后输出，再在 Node 或空白页 Console 运行。这个模型只解释“访问如何被引向应用自己的对象”，没有实现 DOM、路由、宿主函数绑定和卸载；它不能代替真实沙箱。

```js
const makeTeachingSandbox = () => {
  const own = Object.create(null)
  const allowed = { console }
  return new Proxy(own, {
    has: () => true,
    get(target, key) {
      if (key === Symbol.unscopables) return undefined
      return key in target ? target[key] : allowed[key]
    },
    set(target, key, value) {
      target[key] = value
      return true
    },
  })
}
const a = makeTeachingSandbox()
const b = makeTeachingSandbox()
// with 在 strict/module 语法体中不允许；Function 在此创建非严格的教学函数。
const run = new Function('scope', 'with(scope){ count = (count || 0) + 1 }')
run(a)
run(a)
run(b)
console.log(a.count, b.count) // 2 1
```

现在不用术语，解释这条轨迹：A 第一次读到什么、写到哪里；A 第二次为何能读回；B 为什么从自己的初值开始。然后回答四个问题：

1. `has` 在 `with` 的标识符查找里起什么作用？移除它，第一次读取 `count` 会怎样？
2. 为什么 `get` 要单独处理 `Symbol.unscopables`？
3. 如果允许访问同一个原始 `document`，这个模型还缺什么？
4. 如果允许 `setInterval`，删除 a/b 对象为什么不能自动停止定时器？

答案和判定标准在 [第 14 章](14-自测答案与进阶挑战.md)。教学模型使用 `with(proxy)`；真实 MicroApp 的包装还包含 `__MICRO_APP_WINDOW__`、内部函数参数和全局别名，不能直接把这里的 `has: true` 套进真实实现。

## 6. 第一次读源码，只记录四项

先跟 [renderApp](../packages/micro-app2/src/micro_app.ts) → [标签连接](../packages/micro-app2/src/micro_app_element.ts) → [CreateApp](../packages/micro-app2/src/create_app.ts)。每个节点只记四项：输入、关键状态、输出、失败往哪里传播。

```text
函数：
输入：来自谁？携带哪个 name、URL 或容器？
状态：改了哪一份实例、资源或等待条件？
输出：谁继续执行？有没有异步等待？
失败：是 throw、reject、生命周期 error，还是仅记录日志？
```

先读正常首次挂载，再读卸载；然后才扩展缓存复用、UMD 和预渲染。一个分支还解释不清时，不需要同时打开整个 sandbox 目录。

进入第 04 章后，把同样的方法用于两路资源完成；进入第 08 章后，新增“谁创建、谁释放”一列。你最终得到的是自己的执行地图。
