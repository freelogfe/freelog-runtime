# 01 资料来源与版本基线

先回答“我现在维护的究竟是哪一份 MicroApp”。后续章节的行为说明以仓库里的 `packages/micro-app2/src` 为准，官方文档负责解释设计意图，上游源码负责建立对照，不能把最新官网的所有行为直接套到本地。

依据：[GitHub 仓库元数据](https://api.github.com/repos/jd-opensource/micro-app)、[默认分支提交查询](https://api.github.com/repos/jd-opensource/micro-app/commits?per_page=1)、[npm 注册表元数据](https://registry.npmjs.org/@micro-zoe%2fmicro-app)、[新官网](https://jd-opensource.github.io/micro-app/)。这些是本次读取结果，不代表后续一定继续维护，也不构成升级建议。

因此，维护策略可以是“本地 fork 自己负责，选择性吸收上游补丁”。这与上游是否继续更新是两个问题。公司定制逻辑、产品兼容性和生产验收仍然需要自己掌握。

## 2. 本地 fork 的精确基线

本地 [package.json](../packages/micro-app2/package.json) 声明：

```text
包名：@micro-zoe/micro-app
版本：1.0.0-rc.8
module：lib/index.esm.js
main：lib/index.min.js
types：typings/index.d.ts
```

包名和版本没有带公司 fork 标记，因此它们不能单独证明运行的是原版，也不能区分两个不同的内部补丁版本。

本次从官方来源锁定的原版：

| 字段 | 值 |
| --- | --- |
| 上游 tag | `v1.0.0-rc.8` |
| tag 对应提交 | `1d3802735266cd14958601609a51ef2d23b1e915` |
| npm 同版本 `gitHead` | `1d3802735266cd14958601609a51ef2d23b1e915` |
| tag 提交日期 | 2024-08-20 |
| npm 发布日期 | 2024-08-20 |
| npm tarball SHA-1 | `a095bebd053f7e26509b82667cf83bdb8ceef194` |

依据：[固定提交](https://github.com/jd-opensource/micro-app/tree/1d3802735266cd14958601609a51ef2d23b1e915)、[tags API](https://api.github.com/repos/jd-opensource/micro-app/tags?per_page=100)、[rc.8 注册表元数据](https://registry.npmjs.org/@micro-zoe%2fmicro-app/1.0.0-rc.8)。本次下载 tarball 后计算的 SHA-1 与注册表 `dist.shasum` 一致；正式制品校验还应使用注册表的 SHA-512 `dist.integrity`。

本次比较方法是下载该 **固定提交** 的源码归档，与本地相对路径一一对应，归一化 CRLF/LF 后比较文本。另从 npm ESM sourcemap 的 39 个 `sourcesContent` 交叉核对发布源码。sourcemap 不包含全部文件，不能把未被打进 map 的 `src/index.ts` 和 polyfill 错认为本地新增。

结果：本地与原版都有 41 个非测试 TypeScript 源文件；其中 7 个文件存在文本差异，4 个文件包含执行逻辑变化。完整差异见 [第 12 章](./12-Fork差异与持续维护.md)。

## 3. 三类资料分别怎么读

| 资料 | 回答的问题 | 使用限制 |
| --- | --- | --- |
| [平台 Agent 入口](https://widget-docs.devfreelog.com/agents.html) | 平台对象、操作约定、业务任务入口是什么 | 在线文档与运行时生产部署版本不能仅凭网址认定一致 |
| [本地主题插件文档](../packages/docs/guide/index.md)及[Widget API](../packages/docs/api/widget.md) | 平台作者如何开发、挂载和使用主题插件 | 描述面向使用者的契约；有冲突时记录差异并核对实现 |
| [本地 MicroApp 文档](../packages/micro-app2/docs/zh-cn/start.md) | rc.8 的概念、选项和推荐用法 | 是随 fork 保存的文档快照，不等于最新官网 |
| [本地 MicroApp 源码入口](../packages/micro-app2/src/index.ts) | 当前工作树实际如何执行 | 源码变化需要构建后才会进入 `lib` 消费链 |
| [固定 rc.8 上游源码](https://github.com/jd-opensource/micro-app/tree/1d3802735266cd14958601609a51ef2d23b1e915) | 哪些是原版机制、哪些是公司改造 | 不含 Freelog 定制 |
| [当前官网](https://jd-opensource.github.io/micro-app/docs.html#/zh-cn/start) | 了解上游当前说明和后续能力 | 与本地相隔多个 rc 版本，先核对是否在本地存在 |

本次对照中，本地 `start.md`、`sandbox.md`、`router.md`、`static-source.md`、`plugins.md`、`keep-alive.md`、`data.md` 与固定 rc.8 tag 的对应正文在换行归一化后相同。这些章节可作为本地学习材料，但其中示例、注释和描述仍需与源码互证。例如文档列出的插件参数，不应自动视为每个调用点都会传入的参数。

此次还读取了新官网的 sandbox、router、Vite 和 configure 正文。前两套版本并非所有章节都不同：sandbox、Vite 对应正文仍相同；当前 router 多了 pure/state 使用范围提示；configure 出现本地源码和类型中没有的 `inheritBaseBody`、`aHrefResolver`。这个具体差异说明，查询新官网时必须逐项核对本地支持，不能只看同样的产品名称。[当前配置正文](https://jd-opensource.github.io/micro-app/zh-cn/configure.md)、[当前路由正文](https://jd-opensource.github.io/micro-app/zh-cn/router.md)会随上游更新。

## 5. 本手册的证据标记

- **源码事实**：能在引用文件及函数中直接读到的实现。说明的是当前仓库，不自动覆盖线上。
- **推断／风险**：从实现推导的潜在后果，需要实验验证，不能写成已发生故障。
- **建议方案**：供后续开发采用的实现方向；本轮文档工作没有替你修改运行时代码。
- **待验证**：依赖真实浏览器、部署配置、凭据、服务端权限或真实主题插件，静态阅读不能确认的部分。

例如：`CompletionPath` 含有 `baseUrl.pathname + path` 是源码事实；某类无斜杠相对路径可能发生意外拼接是可验证风险；改成明确 URL 解析契约是建议方案；线上所有主题是否受影响是待验证问题。

## 6. 你的第一次源码定位练习

在仓库根目录执行以下只读查询：

```powershell
Get-Content packages/micro-app2/package.json
rg -n 'micro-app2|@micro-zoe/micro-app' pnpm-lock.yaml
rg -n 'renderApp|start\(' packages/freelog-runtime-core/src/structure
rg -n 'CompletionPath|fileHost|HOST_END' packages/micro-app2/src
```

完成后用自己的话回答：

1. 为什么“依赖 workspace 包”不等于“浏览器直接执行 `src`”？
2. 为什么新官网示例能运行，不代表本地 rc.8 支持相同行为？
3. 为什么四处 URL 逻辑变化，比几十个相同的沙箱文件更值得先建立回归用例？

判断标准：能够把包解析入口、原版基线和公司定制三个对象分清。下一步进入 [Freelog 业务与运行时架构](./02-Freelog业务与运行时架构.md)。
