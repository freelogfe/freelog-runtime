本章检查现有实现知识。全书的底层技术与独立架构应先按第一、二部学习，并完成 [综合设计题](CAPSTONE.md)；这里的实现题不能替代它们。

答案用来检查推理，不用来替代实验。每题先写自己的判断、证据和验证方法，再展开。你可以解释实际结果为何与预测不同，但不能把“程序输出了这个值”直接当作合理设计的证明。

本章围绕教学阅读宿主和 `reader-a`／`reader-b` 播放器插件。涉及 `bindName`、展品、依赖和文件授权时，会明确切换到真实 Freelog 代码；教学 data 能力不冒充平台 SDK。

## 1. 如何评分与补救

第 00 章六题沿用每题 0—2 分；本章源码十问每题 0—3 分。迁移挑战单独评价，不与选择学习起点的分数混算。

| 分数 | 源码十问的判定 |
| --- | --- |
| 0 | 结论错误，或只能复述术语 |
| 1 | 结论正确，但缺少因果链 |
| 2 | 能用真实函数／状态解释，并指出一个适用边界 |
| 3 | 还能给出区分其他假设的实验，说明通过或失败如何判断 |

每题至少达到 2 分，且第 8、9、10 题没有把清理、授权或产物边界混淆，再尝试独立补丁设计。3 分强调的是“知道如何证明”；没有实际运行时，实验状态仍需如实写待运行。

答错时只补当前缺口：找对应章节的主路径 → 跑一个最小样本 → 用自己的话重答。不要为了单题重新通读全书。

## 2. 第 00 章六题参考答案

<details>
<summary>D1：独立地址能打开，为什么嵌入还会失败？</summary>

**判断：** 这主要证明顶层导航能取得并运行那个页面。跨源资源 fetch、ESM 依赖图、主页面的 CSP／混合内容约束、沙箱兼容、SDK 上下文和平台授权都尚未因此通过。

**推理：** 顶层页面访问和“另一个 origin 的页面读取其资源”适用的浏览器路径不同。即使入口 HTML 已取到，JS／CSS／动态 chunk 还会各自请求；正确执行脚本之后，也可能缺业务上下文。

**怎样证明：** 保留最早失败请求或异常，区分入口、资源与业务 API；记录实际响应及执行模式。先修最早失败环节，再看后续错误是否消失。不能把所有白屏归为 CORS。

回读：[加载流水线](04-加载流水线与应用生命周期.md)、[能力注入](09-主题插件与Freelog能力注入.md)。

</details>

<details>
<summary>D2：两个播放器使用相同变量与根节点，需要隔离什么？</summary>

**判断：** 普通全局属性的写入归属和 DOM 创建／查询／插入的归属需要分别处理；只有 JS 属性分流不够。样式、导航和异步资源还是其他维度。

**推理：** A/B 的 `window.player` 可以分别保存，但它们若都拿到真实 document，第一个 `#root` 仍可能被两个应用同时使用。即使 DOM 查询正确，未处理的全局 CSS 仍可影响对方。

**怎样证明：** 在两应用各自入口中写同名属性、查询同名根节点，记录实例名与节点标记，并观察真实树位置。只在顶层 DevTools Console 执行，通常不能证明子应用代理路径。

回读：[JavaScript 沙箱](05-JavaScript沙箱与隔离边界.md)、[DOM 与 CSS](06-DOM代理与CSS隔离.md)。

</details>

<details>
<summary>D3：为什么两次 onLoad 不是自动的重复启动？</summary>

**判断：** 当前 `extractSourceDom` 有 CSS／HTML 处理与 JS 资源处理两路。即使某一路没有资源，也会通知 `CreateApp.onLoad`；`++loadSourceLevel === 2` 是汇合条件。

**推理：** 这两个通知表达阶段完成，不是文件数量，也不是两次应用 mount。defer、async、module 等后续执行仍需看 `execScripts`。

**怎样证明：** 给两次回调记录调用栈、name、loadSourceLevel 和 mount 次数。资源文件多于两个并不改变“两路完成”的含义。真正重复挂载还需在标签连接、实例注册或 mount 层寻找证据。

回读：[第 04 章](04-加载流水线与应用生命周期.md)。

</details>

<details>
<summary>D4：改写 location.origin 能改变真实网络权限吗？</summary>

**判断：** 不能。子应用读到的虚拟位置可以用于路由与资源适配；浏览器仍根据真实环境、请求和响应规则实施同源、CORS、Cookie 等约束。

**推理：** 改一个 JavaScript getter 返回值，不会改变发起请求的真实页面 origin，也不会让服务端给予额外权限。

**怎样证明：** 对照虚拟 location 与真实浏览器地址，再检查请求的实际来源和响应头。保持服务端规则不变，只改虚拟返回值，不能据此期待原先被拒的跨源读取变成功。真实授权还要检查服务端业务响应。

回读：[浏览器模型](00-学习路线与浏览器基础.md)、[路由](07-路由虚拟化与导航.md)。

</details>

<details>
<summary>D5：移除 DOM 后，异步工作会自动结束吗？</summary>

**判断：** DOM 移除本身没有这个承诺。计时器、Promise 后续处理、WebSocket 和第三方实例由对应机制及拥有者管理；框架只能清理其代理并记录的部分。

**推理：** Promise 尚可结算，旧回调也可能持有状态或节点引用。即使请求被 abort，仍需判断结果是否属于当前有效的一次挂载。隐藏、普通卸载、UMD 与 destroy 的自动处理也不同。

**怎样证明：** 分别记录旧回调次数、连接与订阅数，做重复进入／退出和旧响应迟到对照；不要只看节点是否消失或某次堆内存是否下降。

回读：[通信与副作用](08-通信与副作用清理.md)、[迟到结果案例](CASE-STUDY.md)。

</details>

<details>
<summary>D6：改源码后刷新无变化，先检查什么？</summary>

**判断：** 先核对真实消费链，再判断补丁逻辑。workspace 链接只决定包目录；本包 `module/main` 指向 lib，主应用还有依赖预构建和最终页面构建。

**推理：** 浏览器可能执行旧 lib 或旧页面资产；类型消费者又可能读取另一份声明。单改 src 不保证任何一端已经更新。

**怎样证明：** 核对包解析、lib 内容及摘要、开发工具缓存和浏览器 Sources／网络取得的字节；消费者类型入口单独检查。记录构建身份，不只看仍为 `1.0.0-rc.8` 的版本字符串。

回读：[Fork 持续维护](12-Fork差异与持续维护.md)。

</details>

## 3. 教学沙箱的四个“为什么”

先看第 00 章模型的执行顺序。第一次执行 A 时，`count` 的标识符查找进入 with 对象；读取结果为空，表达式得到 1 并写入 A。第二次读回 A 的 1 后写 2。B 读取自己的对象，最终写入 1。`2 1` 证明这个模型的普通属性被分流，证明范围仅止于此。

<details>
<summary>为什么需要 has？去掉它会怎样？</summary>

`with` 在查找标识符时需要判断当前对象是否提供这个名字。模型的 `has: () => true` 将 `count` 的查找接到代理，再由 get/set 分流。

如果去掉 has，空目标原本没有 count；在外层也不存在该变量的干净环境中，第一次读取 `count` 会抛 ReferenceError，而不是得到代理 get 返回的 undefined。如果外层恰好已有 count，结果又可能变成读取或修改外层，这也是实验环境需要明确的原因。

真实 MicroApp 没有直接照搬这一模型。当前 [bindScope](../packages/micro-app2/src/source/scripts.ts) 使用 `with(proxyWindow.__MICRO_APP_WINDOW__)`，并传递 `GLOBAL_CACHED_KEY` 中的全局参数；[with/window.ts](../packages/micro-app2/src/sandbox/with/window.ts) 的 has 还处理 scopeProperties 及 `in` 判断。不能把 `has: true` 当成真实包装所有裸变量语义的答案。

</details>

<details>
<summary>为什么处理 Symbol.unscopables？</summary>

`with` 的对象环境会检查 `Symbol.unscopables`，决定哪些属性不参与该层标识符查找。它是控制查找行为的特殊入口，不是播放器业务变量。模型显式返回 undefined，表达“不额外排除属性”。

当前极简 allowed 对象中没有这个 Symbol，去掉该特判通常仍得到 undefined，不能据此断言特判在本样例中不可缺少。它的教学作用是让你认识该控制路径，避免以后把该 Symbol 当普通字段代理到一个意外对象上。

进一步实验可为它返回 `{ count: true }`，观察干净环境中的 count 为什么不再按先前规则解析。先理解规则，再解释结果。

</details>

<details>
<summary>允许访问同一个 document 后，还缺什么？</summary>

模型只存取全局属性；返回同一个原始 document 后，A/B 仍能创建、查询和修改共享节点。需要节点归属、查询范围、插入／删除映射、静态节点与动态资源处理等机制；CSS 作用范围又需单独处理。

这正是 [DOM 与 CSS 章节](06-DOM代理与CSS隔离.md) 解释的职责。不能在这个模型里加一行 `allowed.document = document` 后，称它已具备真实 DOM 沙箱。

</details>

<details>
<summary>为什么删除沙箱对象不会停止定时器？</summary>

计时器由宿主调度并持有回调。对象变量不再被引用，不等于宿主取消了任务；回调自身还可能保持对应用状态的引用。

需要创建时记录句柄，在退出协议中 `clearInterval`／`clearTimeout`，以及明确隐藏是否暂停业务。模型没有这本资源账；真实实现的自动记账范围也要按模式核对，见 [第 08 章](08-通信与副作用清理.md)。

</details>

## 4. 第 13 章源码十问参考答案

<details>
<summary>1．打开 URL 成功，为什么不能证明 fetch、ESM 和授权成功？</summary>

核心答案见 D1。进一步达到 2 分，需要说出至少两个实际分支：入口 fetch 经 [fetchSource](../packages/micro-app2/src/source/fetch.ts)，外部原生 module 可由 [runCode2InlineScript](../packages/micro-app2/src/source/scripts.ts) 设置 src 后交浏览器处理；业务访问则依赖平台上下文和服务端。

达到 3 分的实验：保持同一个插件入口，分别记录入口、普通脚本、module 依赖及一项业务请求。让其中一项失败，比较最早异常和其余成功项；不能只截一张白屏图。

补救：[04 加载](04-加载流水线与应用生命周期.md)、[09 注入](09-主题插件与Freelog能力注入.md)。

</details>

<details>
<summary>2．两次 onLoad 分别证明什么，哪些脚本尚未执行？</summary>

两次分别通知样式／HTML 路与 JS 资源路完成；见 [extractSourceDom](../packages/micro-app2/src/source/index.ts) 和 [CreateApp.onLoad](../packages/micro-app2/src/create_app.ts)。后续还需 mount、等待沙箱准备、执行脚本及处理 UMD 钩子。尤其 defer/async/module 不可由第二次 onLoad 就宣布全部完成。

达到 3 分的实验：延迟一份 CSS，再延迟一份需后续处理的脚本，分别观察第二次 onLoad、execScripts 与 mounted 的时点。记录的是阶段和因果，不用“时间差不多”代替调用栈。

补救：[04 两路汇合与执行顺序](04-加载流水线与应用生命周期.md)。

</details>

<details>
<summary>3．get／has／set 如何影响裸变量和 window.x？</summary>

教学模型中，has 影响 with 的名字查找，get 决定读值，set 决定写入位置。`window.x` 则先取 window 再进行属性访问，不能自动等同于每一种裸变量表达式。

真实实现中，还需同时阅读 [bindScope](../packages/micro-app2/src/source/scripts.ts)、[with 初始化](../packages/micro-app2/src/sandbox/with/index.ts) 与 [createProxyWindow](../packages/micro-app2/src/sandbox/with/window.ts)。外层 with 对象、内部函数的全局参数、window/self 别名以及 scopeProperties／escapeProperties 共同影响行为。顶层 `var` 在包装函数里也不会自然成为 window 属性。

达到 3 分的实验：在测试子应用中分别比较 `var player`、`window.player`、读取一个宿主已有普通属性和一个 scopeProperties；对比 A/B 与真实宿主。明确是经典脚本还是原生 module，不能把两条路径混测。

补救：[05 作用域与代理](05-JavaScript沙箱与隔离边界.md)。

</details>

<details>
<summary>4．iframe 沙箱的可见 DOM 在哪，哪些能力仍共享？</summary>

iframe 提供 JavaScript realm，MicroApp 还通过 document／元素适配把主要可见业务节点放进主页面的子应用容器。脚本节点等有特别路径。它不是直接把整个应用页面显示在一个完全独立的可见 iframe 中。

宿主引用、可见 DOM 整合、部分浏览器能力及同源存储等不能一概当作隔离副本。源码还显式提供 rawWindow/rawDocument；因此该机制不能自动承担恶意插件的安全隔离。

达到 3 分的实验：同时查看隐藏 iframe、真实业务容器与子应用上下文的构造器身份；说明“Array 不同”与“可见节点属于主页面”如何并存。

补救：[05 iframe](05-JavaScript沙箱与隔离边界.md)、[06 DOM](06-DOM代理与CSS隔离.md)。

</details>

<details>
<summary>5．CSS 有前缀，为什么仍需测根规则、动画、继承和弹层？</summary>

普通选择器前缀只是样式约束的一部分。[CSSParser](../packages/micro-app2/src/sandbox/scoped_css.ts) 对 html／`:root` 有特殊处理，未看到按实例重命名所有 keyframes 的机制；宿主的继承属性、通配规则仍可能传入。CSSOM、ignore 资源和动态写法也有边界。

弹层除了样式匹配，还受真实容器、overflow、transform、定位和层级影响。看到丢样式不能立即认定 parser 错误。

达到 3 分的实验：A/B 各挂同名 class 与同名动画，观察普通规则与动画是否具有同样边界；再检查弹层实际父节点和 Computed 中命中的规则。区分“规则没转换”“转换后没匹配”“匹配但被覆盖”三种原因。

补救：[06 隔离边界与弹层诊断](06-DOM代理与CSS隔离.md)。

</details>

<details>
<summary>6．为什么 history.go(-1) 可能影响多个应用？</summary>

虚拟 location／state 不代表每个子应用拥有独立浏览器历史栈。主页面历史仍共享；with 的部分 history 方法和 iframe 的 go 会通向真实 history。一次后退对应的是浏览器历史条目，可能包含 A/B 共同状态。

达到 3 分的实验：A 导航两次、B 导航一次，再后退；每步同时记录 A/B 虚拟路径、真实 URL 和 `__MICRO_APP_STATE__`。如果只看某个路由组件的画面，无法判断真正恢复了哪条记录。state/pure 的可分享性也不能由 search 的结果推断。

补救：[07 路由虚拟化](07-路由虚拟化与导航.md)。

</details>

<details>
<summary>7．为什么通信不能直接当作逐条可靠事件？</summary>

[EventCenter](../packages/micro-app2/src/interact/event_center.ts) 用浅合并、队列、延迟处理和相等判断管理数据。同一轮多次写入可能被合并；缓存可能在新监听注册时被自动触发。off 与 clearData 也分别处理订阅和数据。

因此“发送两次命令，就应该按顺序收到两次独立业务事件”不是默认保证。需要逐条确认的业务，应另定义命令 ID、去重、确认与失败协议；force 只能改变部分通知过滤，不会自动提供这些语义。

达到 3 分的实验：比较同步两次派发、同值派发、新／旧嵌套引用、移除监听后重订阅。解释回调次数与最终状态。不能直接以多次支付等真实动作测试通信语义。

补救：[08 数据通道](08-通信与副作用清理.md)。

</details>

<details>
<summary>8．普通卸载、UMD、keep-alive、destroy 各保留什么？</summary>

首先区分维度：UMD 是由 mount/unmount 钩子检测出的生命周期复用模式；keep-alive 是隐藏／恢复策略；destroy 是更彻底淘汰实例的选项。它们不是四个互斥的“运行模式”。

普通卸载会清容器、停止沙箱并按具体模式释放资源，仍可能保留可复用数据或实例。UMD 路径可保留执行环境，再调用 mount；keep-alive 隐藏保留状态并处理部分副作用，不等于所有后台任务暂停；destroy 删除实例等，但不保证清空所有共享外部 JS/CSS Map。

达到 3 分的实验：使用同一应用对比首次、重挂、隐藏恢复和销毁重建，记录初始化次数、状态保留、计时器／订阅数和应用列表。同步 unmount 抛错、返回 pending Promise 和异步 reject 也应分别分析，不能由一个分支推断最终都能清理。

补救：[04 生命周期](04-加载流水线与应用生命周期.md)、[08 清理](08-通信与副作用清理.md)。

</details>

<details>
<summary>9．bindName 绑定什么，为什么不是安全凭据？</summary>

真实 [widget.ts](../packages/freelog-runtime-core/src/structure/widget.ts) 中，bindName 的 Proxy 在读取函数时返回包装函数，调用时把当前实例 name 加到参数前面。SDK 通过注入的 `data.freelogApp` 获得它，使 `getSelfNid()` 等调用可以查当前实例配置。

这绑定的是调用上下文，不是由服务端验证的不可伪造凭据。普通字段和函数引用在同页共享，沙箱又有宿主引用路径。平台读取内容仍需服务端按真实业务身份鉴权。

达到 3 分的实验：在测试节点跟踪一次 SDK 方法调用，记录从子应用无 name 参数，到 core 收到 name，再查 widgetsConfig 的过程；另外用未授权内容验证服务端仍拒绝。教学实验台的 data 能力只展示引用传递，不能替代这项平台验证。

补救：[02 身份模型](02-Freelog业务与运行时架构.md)、[09 注入链](09-主题插件与Freelog能力注入.md)。

</details>

<details>
<summary>10．如何证明类型消费者和浏览器都取得新产物？</summary>

分别验证两条链。JS 链是 src → 构建 lib → 包解析／预构建 → 主应用资产 → 浏览器字节；类型链是声明生成 → package.types → 消费者解析和类型检查。当前 build 生成位置与 types 入口存在漂移风险，不能由 build 返回 0 推出两端一致。

达到 3 分的验证记录应包含：源码提交与依赖基线、实际 lib／声明入口、构建结果、消费者解析与类型检查、浏览器实际取得的文件或摘要，以及可恢复的上一份产物。`sources.json` 摘要只证明被记录文件是否变化，不证明 src/lib 等价，更不证明生产已部署。

补救：[12 构建、类型与回退](12-Fork差异与持续维护.md)。

## 5. 基础迁移：改变返回结果与工作边界

### A：新请求已经成功，旧请求随后失败

沿用 [完整案例](CASE-STUDY.md) 的顺序，令 new 成功后，再让 old 拒绝。有人只在 `.then` 中检查代次，`.catch` 直接显示错误。当前视图会怎样？怎样保留错误证据又不把新页面改成错误页？

<details>
<summary>参考推理与验收</summary>

成功与失败都是异步结果，都要验证提交权。旧 catch 若直接更新 UI，仍会覆盖新一代的成功状态。catch 应捕获原始错误，在 UI 提交前检查活跃性与代次；过期错误可以记录为带旧代次的诊断，但不能更新当前错误面板或发当前失败信号。

验收至少包括：新成功后旧失败不改变视图；当前请求失败按合同展示错误；旧失败被观察与处理，不产生未处理拒绝；A 的失败不影响 B。不要用空 catch 吞掉所有错误，也不要把旧错误当新成功。

当前 `pending-result` 教学模型把拒绝交给调用方，现有测试只证明拒绝传播；它没有实现带错误 UI 的完整方案。本题要求你补充错误状态及断言，不能把既有五项通过当成本题通过。

回读：第 03 章的结果协议、第 08 章的结果提交权与 CASE 第 6—7 节。

</details>

### B：没有卸载，但用户快速切换章节

播放器一直保持可见，先请求 chapter-1，再请求 chapter-2；chapter-2 先返回。只在 mount 时递增代次能否挡住 chapter-1？如果同时还有独立的音量保存请求，是否该和章节请求共用一个令牌？

<details>
<summary>参考推理与验收</summary>

工作有效期不一定等于挂载有效期。若两次章节请求都读同一个挂载令牌，它们会同时通过检查，旧章节仍可覆盖新章节。每次新的章节意图应产生新的章节请求令牌，同时保留挂载是否有效的检查。

互不替代的工作可以用独立令牌，例如章节选择与音量保存。不能让切章节把并不冲突的保存结果一并判为过期；也不能无限拆令牌，导致本来互斥的章节渲染不再有统一所有者。

验收包括：同一挂载内新章节优先；正常最新结果仍可提交；退出后所有该实例 UI 工作失效；独立音量保存不被无关章节切换误取消；A/B 使用各自的令牌，不用一个全局数字管理所有播放器。

回读：第 03 章四份身份、第 08 章资源账本与 CASE 的代次模型。先写确定性排程，再接真实网络。

</details>

## 6. 进阶挑战一：旧请求已失效，旧能力引用还活着

先独立设计，再展开评价。你已经给 [迟到结果案例](CASE-STUDY.md) 增加了挂载代次检查：旧响应不能覆盖新画面。现在发现一段由宿主创建的回调仍持有 A 次挂载的教学能力对象，A 卸载后它还可以调用 `reportProgress()`；B 次挂载使用同一个 `reader-a` 名称。

请回答：拦住旧 UI 提交是否足够？能力对象应该属于资源、实例名，还是某次有效挂载？怎样拒绝旧引用而保留 B 的能力？你会在哪一层检查，并用什么对照证明没有误杀？

<details>
<summary>查看评价准则与参考推理</summary>

**应识别的边界：** UI 结果提交权和宿主能力调用权是两条路径。一个 generation guard 没有被宿主能力调用时，就不能替它验证有效性。name 可复用，不能单靠相同 name 判断调用仍有效。

**可接受设计：** 让能力封装携带某次挂载的身份或有效性令牌，在宿主入口检查当前有效状态；退出时撤销旧令牌，B 使用新的令牌。具体使用 generation、对象身份或显式 revoke 由现有协议决定。先写清返回拒绝还是抛业务错误，不能静默丢弃关键动作。

**必须包含的对照：** A 有效时成功；A 卸载后旧引用被拒；B 的新引用成功；另一个 `reader-b` 完全不受影响；重复撤销幂等。仅清空子应用局部变量，无法处理宿主已持有引用。

本题讨论的是能力有效期设计，不意味着真实 Freelog SDK 已具备该机制；也不能把客户端令牌当作服务端授权替代。达到要求需同时解释这一边界。

</details>

## 7. 进阶挑战二：旧控制器迟到，按 name 清理误杀新应用

父视图发起插件挂载后立即退出。挂载 Promise 尚未完成，父视图重新进入，用相同最终 name 发起新挂载。旧调用随后返回一个控制器，其 `unmount()` 按 name 转发给引擎。有人建议：“旧父视图已退出，就对旧控制器立即 unmount。”

请判断：建议在哪种前提下成立？name 被复用后有什么风险？给出不用猜延时的协调方案，并说明异常、超时和永不结束 Promise 如何影响它。

<details>
<summary>查看评价准则与参考推理</summary>

**关键识别：** 控制器是旧对象，不代表其 `unmount()` 操作绑定旧引擎实例。当前 [mountApp](../packages/freelog-runtime-core/src/structure/widget.ts) 的包装按 `widgetRenderName` 调用 `microApp.unmountApp`；若同名已对应新的应用，旧控制器清理可能指向新对象。真实引擎还会检查运行中同名冲突，所以题目也不能假定并发一定允许第二次成功。

**两条可评估方案：** 一是按最终 name 串行协调挂载和清理，前一代结果归属解决后再允许复用；二是为不同生命周期分配明确不同的实例身份，再处理退出与资源淘汰。若要引入实例绑定控制器，则须调整接口与一致性协议，不能只给外层对象加一个数字。

**必须分析的失败路径：** 单纯 `Promise.race` 超时并未取消底层挂载；把超时后新请求直接放行，仍可能撞上迟到旧请求。协调器需要明确哪些底层任务还在执行、如何隔离未决实例，以及何时可安全释放 name。不能用固定 300ms 等待代替证明。

**通过所需证据：** 可控延迟复现旧先到／新先到，确认退出后不残留无人拥有实例，新挂载不被旧控制器卸载，另一个插件不受影响。记录冲突、挂载失败、清理失败和 pending 的可见结果。

这与“同一实例的旧网络响应覆盖新画面”相关但不同：一个管理引擎实例与控制器所有权，一个管理异步结果提交权。能说清差别，才算完成迁移。

</details>
