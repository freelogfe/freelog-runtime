# 08 通信与副作用：挂载成功之后，如何正确退出

[返回目录](README.md) · [上一章：路由虚拟化](07-路由虚拟化与导航.md) · [下一章：Freelog 能力注入](09-主题插件与Freelog能力注入.md)

本章目标：解释 MicroApp 通信的合并与异步语义，区分“隐藏、卸载、销毁”，为监听器、定时器、请求和应用实例建立成对释放的合同。先做 [实验台的消息与退出](11-分层实验与验收矩阵.md)，再对照下面的资源账本；具体已测范围见 [验证记录](VALIDATION.md)。修复设计仍是建议，不表示已改内核。

## 1. 数据通信解决什么，不能替代什么

主应用给主题传配置，主题向宿主报告状态，插件之间交换选中的资源 ID，这些是通信。资源授权和请求身份则是平台能力合同，不能因收到一条消息就认为用户有权读取资源。

MicroApp 当前通信主要是同一页面内的 EventCenter，不是不同 origin 之间的 postMessage 安全通道。消息里的函数和对象引用可能直接共享；没有自动深拷贝、类型验证或权限判断。

## 2. 真实通道与数据流

入口见 [interact/index.ts](../packages/micro-app2/src/interact/index.ts)，内核见 [event_center.ts](../packages/micro-app2/src/interact/event_center.ts)。

| 发方 → 收方 | 发送 | 监听 | 内部通道 |
| --- | --- | --- | --- |
| 主 → 某子应用 | `microApp.setData(name, data)` | 子 `window.microApp.addDataListener(cb)` | `__name_from_base_app__` |
| 子 → 主 | 子 `window.microApp.dispatch(data)` | 主 `microApp.addDataListener(name, cb)`，或容器 datachange | `__name_from_micro_app__` |
| 全局广播 | `setGlobalData(data)` | `addGlobalDataListener(cb)` | `global` |

注意主侧 `getData(name)` 默认读取子发来的数据，子侧 `getData()` 默认读取主发来的数据；clearData 的方向默认值又随侧别不同。调试时把来源方向写全，不要只说“清了 data”。

### 它是异步合并的状态通道

`EventCenter.dispatch` 要求普通对象，把新对象浅合并到 tempData 或旧 data，并用队列和 `defer(this.process)` 处理。同一轮多次发送可能合并；浅相等比较决定是否通知，force 可绕过相等过滤。

```js
// 概念示例：两次同步写入不是两个可靠、独立的业务事件。
microApp.setData('reader', { currentId: 'a' })
microApp.setData('reader', { currentId: 'b', tab: 'detail' })
```

收方可能主要观察最终合并状态。对象里修改同一引用的嵌套字段，还可能无法触发预期的浅比较变化。推荐每次构造新对象；若必须逐条处理支付、授权、交易等命令，另建带 commandId、确认、去重和错误处理的业务协议。这是建议设计，不是现有 EventCenter 自动保证。

`on(..., autoTrigger)` 可以在注册时收到已有缓存。卸载再挂载后的“旧消息”往往是缓存语义，而不是网络又发了一遍。`off` 删除监听器但不清缓存，`clearData` 清数据但不等同删监听器。

## 3. 应用生命周期是一组资源合同

沿 [create_app.ts](../packages/micro-app2/src/create_app.ts) 的 `unmount → handleUnmounted → actionsAfterUnmounted → sandBox.stop` 阅读。UMD unmount 可以返回 Promise，后续清理等待它结束；拒绝后会记录并继续 nextAction。若同步 unmount 抛错，则需要阅读外层 catch 后的实际行为，不能据异步分支推断一定最终清理。

| 动作 | 应理解的语义 | 开发者不能忽略的部分 |
| --- | --- | --- |
| keep-alive 隐藏 | 应用和状态保留；部分全局监听会记录、释放，重显时恢复 | 隐藏不等于后台活动全部暂停 |
| default 模式卸载 | 删除/释放多种代理记录；后续重挂重执行逻辑 | 所有没有被代理记账的资源仍需应用释放 |
| UMD 模式卸载 | 保留部分脚本状态，调用 mount/unmount；快照用于重挂 | mount 必须可重入，unmount 必须完整且幂等 |
| destroy | 更彻底删除实例/缓存，并强制清数据等 | 仍不能替应用保证外部服务、对象引用和异步任务都已结束 |

## 4. 自动清理的覆盖范围

### with：事件、计时器、通信是三本账

[with/window.ts](../packages/micro-app2/src/sandbox/with/window.ts) 的 `patchWindowEffect` 维护 eventListenerMap、intervalIdMap、timeoutIdMap 与快照。事件按类型可能绑定应用容器或真实 window；[with/document.ts](../packages/micro-app2/src/sandbox/with/document.ts) 另记 document 监听和 onclick。

[with/index.ts](../packages/micro-app2/src/sandbox/with/index.ts) 的 `releaseGlobalEffect` 决定 clearTimer：普通 default 卸载或 destroy 才清相应计时器；UMD 卸载、keep-alive 和预渲染保留路径不能称为“自动暂停所有定时器”。快照重建主要重绑事件，不是替你将业务工作队列恢复成原样。

通信监听用 `recordDataCenterSnapshot` / `rebuildDataCenterSnapshot` / `resetDataCenterSnapshot` 处理。global 回调带 appName 标记，用于按应用清理，宿主注册的回调也有自己的所有权。

### iframe：不要照搬 with 的计时器结论

[iframe/window.ts](../packages/micro-app2/src/sandbox/iframe/window.ts) 的 `patchWindowEffect` 主要记事件，未实现与 with 一样的 intervalIdMap。默认卸载或 destroy 会走删除 iframe；UMD 保留 realm 的路径行为不同。因此分别测试，不能用一次 with 演示证明 iframe 的 keep-alive 也会暂停工作。

### 请求和其他浏览器资源

[request.ts](../packages/micro-app2/src/sandbox/request.ts) 对 with 的 fetch/XHR 主要补相对地址并清 DOM 上下文，没有按应用追踪并取消所有在途请求。EventSource 有专门记录与关闭逻辑，with 的 stop 又有模式条件。

WebSocket、Worker、MutationObserver、ResizeObserver、requestAnimationFrame、第三方库实例以及应用主动保存的 DOM 引用，不能仅凭沙箱存在就假定已自动释放。使用者应显式 close / terminate / disconnect / cancel / dispose。

### 给 reader-a 建一张资源账本

先问“谁拥有资源和持有引用”，再问“哪一个 realm 最初发起”。A 通过注入函数让宿主注册了一个回调，这份回调可能保存在宿主数组中；销毁 A 的 iframe 不会自动清空宿主数组。

| 资源 | 创建与持有位置 | 隐藏时的业务选择 | 真正退出时的责任 | 证明没有残留 |
| --- | --- | --- | --- | --- |
| 播放进度计时器 | 子应用 window；回调持有当前视图 | 显式暂停或允许继续，不能靠“不可见”推断 | 清 timer，清引用；框架自动账本仅作已有覆盖 | 退出后计数停止；重挂不多一份 |
| resize／文档监听 | 子应用注册，可能实际绑定真实对象 | 按协议保留或暂停 | 使用同一 callback 和 capture 移除 | A 退出后真实事件不再调用 A；B 仍响应 |
| 章节请求 | 业务服务持有 Promise，回调闭包持有代次 | 可取消或保留，但提交规则要明确 | abort 尽力取消；代次禁止旧结果提交 | 新先旧后排程仍只绘制新结果 |
| 宿主订阅 | 注入能力里的宿主 Set／数组 | 明确宿主是否暂停发给隐藏实例 | 宿主给 unsubscribe，由使用者释放 | 查看宿主订阅数；不能只数 iframe |
| 子插件控制器 | 父插件持有，core 另有登记 | 子插件与父隐藏语义需约定 | 回收迟到控制器、解除父子关系 | 引擎列表、core Map、DOM 三者一致 |
| JS/CSS 共享缓存 | 引擎按 URL 维护的 Map | 可以保留 | 按缓存预算管理，不随单实例盲目清空 | A 销毁后 B 仍正常；增长符合版本／URL数 |

第三行在 [完整案例](CASE-STUDY.md) 中有可运行的错误与修正模型；其余行需要在真实持有者上分别取证。一张堆快照不能证明全部责任已经解除。

能力接口的建议形状是 `const stop = host.subscribe(callback)`，约定 stop 幂等；如果现有 API 仅追加回调而不提供移除，要把它记成明确接口缺口，不能在文档里假装已经可取消。对于当前 `onLogin/onUserChange` 见第 10 章。

## 5. 一个可落实的应用清理写法

下面是建议放进测试子应用的模式，调用 `mount` / `unmount` 的方式应与该应用现有接入协议一致。它展示成对管理，不要求所有业务改成新框架。

```js
let cleanups = []
export function startFeature() {
  stopFeature() // 幂等重建，避免重复绑定
  const controller = new AbortController()
  const onResize = () => { /* 测量当前应用布局 */ }
  const onData = data => { /* 校验协议后更新状态 */ }
  const timer = window.setInterval(() => { /* 刷新非敏感状态 */ }, 5000)
  window.addEventListener('resize', onResize)
  window.microApp?.addDataListener(onData, true)
  cleanups = [
    () => controller.abort(),
    () => window.clearInterval(timer),
    () => window.removeEventListener('resize', onResize),
    () => window.microApp?.removeDataListener(onData),
  ]
  // 若此功能发 fetch，在调用处使用 controller.signal。
}
export function stopFeature() {
  for (const dispose of cleanups.splice(0)) {
    try { dispose() } catch (error) { console.error('feature cleanup', error) }
  }
}
```

同时销毁框架根实例、弹层、编辑器、播放器等。异步请求即使 abort，也应通过实例代次或 disposed 标记防止旧结果更新已卸载 UI。keep-alive 若要求隐藏时停播放/轮询，要在项目的隐藏/显示事件合同里显式暂停和恢复，不能等待框架替你猜。

## 6. 维护者应验证的候选问题：capture 监听释放

当前 window/document 的 addEventListener 包装会记录 listener 和 options，但某些 release 循环调用原生 removeEventListener 时没有传 options。浏览器移除监听需要匹配 capture；因此 capture=true 是一个源码支持的泄漏疑点，尚不能把它写成已经在生产复现的事故。

最小实验流程：

1. 测试子应用通过代理 window 和 document 分别注册 `capture: true` 的自定义事件监听，用控制台打印 appName。
2. 卸载应用，在主页面真实 window/document 发同名事件，观察旧应用回调是否仍触发。
3. 与 capture=false、同函数分别注册两种 capture 的结果对比；再测 UMD 卸载重挂及 keep-alive 隐藏/重显。

如果确认，建议修复范围是“监听记录的身份与移除参数匹配”：以 type、callback、capture 记录，而不是单纯 Set(callback)，重建与释放都使用匹配信息；同时处理对象 listener、once、AbortSignal 等合同。仅在 remove 时读 callback 上的最后一个 options，不能完整解决同 callback 双 capture 覆盖。先写失败回归，再改这些独立分支。

## 7. 通信实验：观察合并与缓存

在测试主应用中导入实际 microApp 单例，注册来自子应用的监听；在子应用入口使用它自己的 `window.microApp`。不要把两侧同名对象搞混。

```js
// 子应用代码：同步 dispatch 两次，观察宿主收到多少次、最终对象是什么。
window.microApp.dispatch({ handbookA: 1 })
window.microApp.dispatch({ handbookB: 2 })
```

主侧注册 `microApp.addDataListener(name, callback, true)`，打印接收对象的安全字段。再给同字段同值、相同嵌套引用、新嵌套引用以及 forceDispatch 分别做实验；卸载重挂，分别验证“只删监听”和“监听加清数据”的区别。验收标准是能从浅合并、队列、缓存解释观察结果，而不是以为所有 dispatch 都一对一送达。

## 8. 如何证明卸载真的有效

用同一测试应用连续挂载/卸载 20 次，分别测 default、UMD、keep-alive 隐藏重显、destroy；再加一个始终保留的 B 应用作为隔离对照。

记录每轮：监听回调次数、活动轮询/连接数、残留弹层节点、隐藏 iframe 数、堆快照中的 detached 节点和外部库实例。通过条件不是“堆数字一次下降”，而是稳定操作后资源数量不随轮次持续增长，旧实例不再响应，B 不受 A 清理影响。GC 具有时机差异，需在相同等待/收集条件下比较。

当前核心测试目录 `src/__tests__` 不在检出树中；`jest.config.js` 列了路径也不能证明这些用例已存在。为上述模式建最小浏览器回归夹具，比直接跑完整 dev 多框架矩阵更适合先恢复一人维护能力；扩大覆盖应由实际故障和接入范围驱动。
