# 架构 03：交付、安全、性能与演进是同一份运行合同的另一半

[上一章：运行时协议](02-从零设计加载器与运行时协议.md) · [下一阶段：MicroApp实现对照](../MICROAPP-MAPPING.md) · [综合设计题](../CAPSTONE.md)

一个应用在开发服务器中成功 mount，只验证了很小的一段。完整架构还必须使“哪些字节被执行、哪些权限被授予、哪些资源被保留、失败如何恢复”可解释。

本章继续保持产品无关；结尾才把设计交给具体实现检查。本轮没有修改生产发布、权限或监控系统。

## 1. 把开发交付和生产交付拆成两套合同

开发应用可能依赖 HTML 注入的 HMR client、React Refresh preamble、按请求转换的 JSX／SFC、开发服务器的模块改写和 WebSocket。生产应用则可能依赖 hashed chunk、CSS拆分、modulepreload、public base、legacy runtime、manifest及缓存。

因此接入矩阵至少包含：

| 维度 | 必须独立核验 |
| --- | --- |
| 开发 | 完整HTML变换、入口与模块依赖、HMR连接、热更新后的状态和副作用 |
| 生产现代产物 | 所有chunk与CSS可寻址、模块格式、lazy路由、跨域与策略 |
| 生产legacy产物 | 对应加载器、polyfill、全局runtime、格式与现代脚本选择 |
| 嵌套／多实例 | 同一代码不同实例、共享依赖与资源版本、退出对照 |

当前仓库的两个主应用还存在实际格式差异：移动端配置启用了 legacy 且关闭现代 chunk。因此将来分析本地实现时，不能只测一个 Vite 开发页就宣称覆盖全部平台。该本地证据在构建章节中展开。

## 2. 用不可变版本图理解部署

一次发布不是“换一份 index.html”，而是换一个从入口可达的资源图：

```text
manifest v7
  → HTML／entry v7
  → shared/runtime chunk v7
  → lazy chunk v7 + lazy CSS v7
  → font/image/worker等资产
```

更新指针之前，新图应可取回；旧会话仍可能沿旧入口请求旧 lazy chunk，因此还需要旧资源保留期与回退。不能在上传新 HTML 的同时删除旧 chunk，然后把偶发 404 归因给微前端沙箱。

hashed文件名帮助识别字节，但并不自动提供原子发布。manifest、CDN缓存、服务端目录与入口引用需要一致。回退也应恢复一张兼容的图，而不是随意退某个 JS 文件。

这属于架构约束，具体缓存头与保留时间要根据发布频率、客户端会话和资源预算确定，不在讲义中编造统一阈值。

## 3. 五层缓存要分清谁拥有清理权

| 缓存层 | 缓存什么 | 一般不能由什么动作清掉 |
| --- | --- | --- |
| HTTP／CDN | URL对应的响应 | 单应用unmount |
| 原生模块图 | 解析URL对应模块与求值状态 | 简单删除自定义Map |
| 构建runtime | Webpack模块表、chunk状态等 | 删除容器DOM |
| 微前端定义／资源缓存 | 定义加载、处理结果 | 未经引用判断的单实例destroy |
| 业务实例／视图缓存 | store、组件状态、KeepAlive等 | 与代码缓存采用同一个无限保留开关 |

当“第二次打开还是旧代码”时，应先检查哪层命中、入口与字节是什么。随机 query 可以暂时改变某层身份，却可能留下多张模块图、重复副作用和新旧依赖混配。

## 4. 安全前提决定能力形式

需要写进设计的不是一句“使用沙箱”，而是：

```text
代码是否被信任？
它可访问宿主document、storage、全局函数与原型吗？
它拿到的能力是否受实例／工作有效期约束？
服务端如何判定节点、展品、依赖与访问者的权限？
退出后旧引用是否继续有效？
```

可信同页应用可以选择函数能力和对象传递，但应承认这些引用共享。非可信代码可能要求跨源文档与受控通信；即使如此，宿主授予的消息操作仍需最小权限、来源和输入协议。跨源不替代服务端业务鉴权。

若同页脚本能访问宿主原始对象，Proxy或浅freeze不足以构成恶意代码边界。CSP、跨源资源、Cookie和模块MIME也必须与交付方式一致；不能让生产部署通过“永久放开所有策略”来弥补加载器假设。

## 5. 性能应按阶段和共享资源测量

不要只记录一个 mounted 时间。至少把定义下载、依赖请求、解析／编译、框架提交、业务关键数据、交互就绪分开。它们可能重叠，因此不是把各段简单相加。

| 观察 | 可能应该优化的层 | 不足以解释它的动作 |
| --- | --- | --- |
| 请求数多但执行短 | 资源图、预加载、共享与缓存 | 重写Proxy |
| 同步初始化长 | 业务初始化、模块顶层副作用、框架渲染工作 | 仅把整个工作塞入一个空闲回调 |
| 隐藏应用仍占工作 | 播放／轮询／连接的可见性策略 | 假设KeepAlive天然暂停 |
| 挂载轮次越多越慢 | 订阅、timer、root、外部服务持有引用 | 只看一次堆内存下降 |
| 发布后lazy失败 | 版本图和旧资源保留 | 盲加重试或重新创建root |

预取资源、预解析和预渲染是不同成本。预渲染会执行代码，可能提前请求业务或建立连接。应该按应用能力决定能否安全预先执行，而不是越早越好。

## 6. 观测字段要能重建一条因果链

建议最少记录：定义／版本、实例与拥有者、工作序号、框架及适配模式、阶段、资源URL类别、结果与耗时。记录敏感请求应脱敏；不需要把完整能力对象或登录态打印出来。

错误至少应区分：定义不可用、模块链接／执行失败、适配器mount失败、框架提交／业务ready失败、取消／超时、cleanup失败、版本或权限不匹配。

同一个错误对象应保留最早原因。不能把加载失败最终统一变成“app timeout”，也不能吞掉cleanup错误只显示成功退出。

## 7. 单人维护时，怎样控制组合爆炸

支持矩阵是承诺范围，不是宣传列表。对每类应用记录构建版本／格式、框架版本、执行模式、路由策略、共享依赖、弹层容器和已测操作。

先维持两三个真正存在的关键组合，再按真实需求扩展。加入一种新格式时，至少验证初次进入、懒加载、重挂、多实例、取消和退出；加入共享依赖策略时，再验证版本不匹配与模块对象身份。

将回归分层：纯协议测试证明对象所有权与异步时序，构建探针证明产物结构，真实浏览器证明框架与DOM行为，平台节点证明业务身份和授权。某一层通过不能替代另一层。

## 8. 演进的最小单位是一个可证明的兼容变化

先冻结可用基线与回退图；明确某项新需求改变了哪条合同；补失败样本；在最靠近责任的位置修改；再覆盖受影响组合。

例如为了兼容一种原生模块产物：先验证其URL、MIME、依赖、全局与ready语义；再决定是新增加载适配、调整框架入口还是修改现有兼容层。不要把模块格式问题、业务授权问题和CSS问题放进一次全局沙箱重写。

## 9. 一份完成的架构决策应当长什么样

```text
需求：多框架插件独立交付、同代码多实例、父视图退出可清理。
前提：代码信任级别、已有兼容范围、部署策略明确。
决定：按应用类别选择交付/执行方式；通用实例协议与框架适配分开。
代价：每条兼容通道都维护自己的模块、样式、路由与生命周期合同。
验证：定义缓存与实例隔离；取消/失败/cleanup；产物图；浏览器；平台授权。
边界：不把状态隔离说成权限隔离，不把dev成功说成prod成功。
回退：保留可识别的完整版本图及对应协议配置。
```

这份决策不需要先提任何库的名称。下一阶段再问：某个具体框架实现了哪些部分，采用了什么机制，在哪些地方改变原生语义，哪些承诺仍落在使用者身上。
